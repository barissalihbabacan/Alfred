# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

B.U.T.L.E.R. Alfred — a personal AI executive-assistant/agent system for Barış (*Barış's Unified Task, Logic, Execution & Reasoning*). Alfred is a British-butler-persona cognitive agent: a vendor-agnostic TypeScript core (`src/`) handles LLM providers, long-term memory, voice and tool execution; the production front end is a Next.js app built as a static export (see **Front end** below). Deployed through Firebase.

## Architecture

Full detail lives in `docs/ARCHITECTURE.md` — read it before touching `src/alfred/` or `src/data/`. Planned capabilities, what each needs, and the pattern for adding a tool to production are in `docs/FEATURE_ROADMAP.md`. Summary of the invariants that matter most:

### Layout
- `src/alfred/` — Alfred's domain logic, split into three "planes": **cognitive** (context, memory — Alfred's understanding of state), **control-plane** (tool routing, permissions), **execution-plane** (capabilities Alfred can invoke). Kept as vendor-independent as possible.
- `src/ai/` — provider-agnostic LLM abstraction. Nothing outside `src/ai/providers/` should import a concrete provider directly; always go through `getAIProvider()` (`src/ai/providers/factory.ts`), switched via `ALFRED_LLM_PROVIDER` (`ollama` | `groq`).
- `src/ai/tools/` — tool definitions the model can call (`types.ts` defines `ITool`, `ToolDefinition`, `ToolCall`, `ToolResult`, `ToolExecutionContext`). Currently `ssh/` (connect, execute, list-directory tools and `ssh-tool-definitions`; not offered in production) and `time/` (get-current-time, current-time, timezone-resolver; shared with production).
- `src/voice/` — STT (Groq Whisper) and TTS (`ITTSProvider` abstraction with mock/fallback, browser Web Speech used in frontend).
- `src/data/` — persistence abstractions: Firestore repositories, vector store, embedding providers. Always accessed through interfaces + factories (e.g. `getConversationRepository()`, `getVectorStore()`, `getEmbeddingProvider()`), each with an in-memory implementation used by unit tests.
- `src/core/` — cross-cutting config, errors and logging. `logging/` is a small JSON-to-stdout `StructuredLogger` (not wired into production; `functions/index.js` has its own `logEvent()` on `firebase-functions/logger`). `events/`, `types/`, `permissions/` are still empty placeholders.
- **Structured logs**: the `api` function emits `llm_request`, `llm_provider_fallback`, `llm_rate_limited`, `llm_stream_error`, `tool_call`, `memory_retrieval` and `memory_extraction` events (tokens, latency, TTFT, scores, outcomes; never API keys, ID tokens or user message text). Query them in Cloud Logging with `jsonPayload.event="llm_request"`.
- `apps/web/` — see **Front end**.
- `functions/` — Firebase Cloud Functions backend (plain JS, separate `package.json`/deploy cycle). Not a thin layer: `functions/index.js` is ~1360 lines and carries its own tool wiring, request handling and two entry points (its chat system prompt now comes from `src/ai/prompts/alfred-system-prompt.ts`) — `api` (`onRequest`, behind the `/api/**` Hosting rewrite) and `alfredCallable` (`onCall`). It is being migrated to import from `src/` (bundled with esbuild, see **Functions bundle** below), but most of it is still hand-written: except for the modules listed there, changes to Alfred's behaviour often need to be made here **and** in `src/` — those parts are not shared code.
- `users/` — canonical, git-versioned, **read-only-at-runtime** profile of Barış (`USER_PROFILE.md`, `PREFERENCES.md`, `WORKING_STYLE.md`). Never written to by the running app. **The prompt carries a reviewed digest of these files, not the files themselves.** Rendered verbatim they cost ~2,000 tokens a turn, most of it repeating the persona, so the prompt's `CANONICAL USER PROFILE` block is `src/alfred/cognitive/context/user-profile.digest.md`: a hand-written condensation (~620 tokens) that keeps the facts and rules that change answers. Its header records the sha256 of each `users/*.md` it was written from. `scripts/generate-user-profile-sources.mjs` embeds the files (`USER_PROFILE_SOURCES`) and the digest body (`USER_PROFILE_DIGEST`) in the committed `user-profile.generated.ts` (nothing reads files at runtime in the bundle). Editing `users/*.md` therefore needs a digest update before it can ship: `npm run generate:user-profile`, `tests/unit/user-profile-renderer.test.ts`, `tests/unit/functions-system-prompt.test.ts` and `functions/build.js` all fail until the digest's hashes match, and the script prints the new hash lines. Update the digest text to reflect the edit, paste the hashes, and refresh the prompt fixture (see **Commands**). In src/, `ContextBuilder.formatUserProfileBlock()` uses the digest when the loaded files are the committed ones; any other sources (e.g. a test directory) are rendered verbatim by `renderUserProfileBlock()` (`user-profile-renderer.ts`), so a different profile is never silently swapped for the digest.
- `docs/persona/ALFRED_PERSONA.md` — canonical behavioral/linguistic spec for Alfred (British-butler tone, pushback style, "sir" usage, response length rules). Consult this before changing anything under `src/alfred/persona/` or `src/ai/prompts/`.

### Front end — one Next.js app, built as a static export
- `apps/web/` (`app/`, `components/`, `lib/`) is the only front end. `next.config.mjs` sets `output: "export"`, so `npm run build:web` writes plain static files to `apps/web/out` and Firebase Hosting serves that directory. There is **no server runtime**: no route handlers (`app/api/*` was removed), no SSR, no middleware. Anything that needs a server belongs in `functions/index.js`.
- `components/VoiceChatPlayground.tsx` is the chat UI; `components/LoginScreen.tsx` is the auth gate; `app/page.tsx` only mounts the chat once Firebase has restored an allowed session.
- All backend calls go through `lib/api.ts` (`apiFetch`), which targets `/api/*` and adds the Firebase ID token (`Authorization: Bearer`) and the App Check token (`X-Firebase-AppCheck`). The `/chat` SSE stream is parsed by `lib/sse.ts`. Don't call `fetch("/api/...")` directly.
- `npm run dev:web` rewrites `/api/**` to `ALFRED_API_ORIGIN` (default: the Functions emulator, `http://127.0.0.1:5001/butler-alfred/us-central1/api`; use `https://butler-alfred.web.app/api` to hit production). The rewrite exists only in dev; the export uses the Hosting rewrite.
- Speech input is the browser Web Speech API (`SpeechRecognition`) and speech output is `speechSynthesis`. There is no server-side STT endpoint in production (the old Next `/api/stt` Groq Whisper route was unused by the UI and was removed with the other route handlers).
- The previous vanilla-JS front end (`apps/web/public/*.js`) was removed in favour of this app.

### Tool execution
`ToolRegistry` (`src/alfred/control-plane/tool-router/tool-registry.ts`, singleton via `getToolRegistry()`) holds `ITool` implementations; `ToolRouter` (`getToolRouter()`) dispatches model tool-calls to them. `PermissionManager` (`src/alfred/control-plane/permission-system/`) gates execution through `ToolExecutionContext extends PermissionContext`. Role policy (least privilege, a missing `userRole` counts as `guest`): `READ_ONLY` anyone; `SAFE_READ`/`WRITE` owner or admin; `EXECUTE` owner only; `DESTRUCTIVE` owner only and with `confirmed: true`. `tests/unit/permission-manager.test.ts` pins the full level × role matrix. This governs `src/` tools only; production tools in `functions/index.js` are single-user and protected by the ID-token gate.

SSH is the only real capability so far. `src/alfred/execution-plane/ssh/` holds the machinery: `ssh-client.interface.ts` with a real `ssh2-client.ts` and a `mock-ssh-client.ts` for tests, plus `ssh-connection-manager.ts`, `remote-command-executor.ts`, `command-registry.ts` (allow-list of runnable commands), `ssh-path-sandbox.ts` (path confinement) and `ls-parser.ts`. Hosts are referred to by alias (`home-server`), never raw credentials in tool arguments.

**Production does not use any of it, and offers no SSH tools.** There is no SSH connection behind `functions/index.js`: the ssh_* tools used to return canned results (a fixed 15-entry `Belgeler/` listing and fixed `df`/`pwd`/`whoami`/`uname` output) that Alfred presented as real server state. They were removed from the tool list: production sends only `get_current_time`, an unexpected `ssh_*` call gets `Tool … not recognized.`, and the persona (built with `sshAvailable: false`, the default) says server access is not connected and forbids inventing server state. `buildAlfredSystemPrompt({ sshAvailable: true })` restores the SSH instructions byte-for-byte for a caller that really executes them. The three tool definitions and argument rules (default host `home-server`, default path `Belgeler`, exact-match allow-list, path deny-list) remain in `src/ai/tools/ssh/ssh-tool-definitions.ts` for the src tools, which add the real-SSH guards (non-string host/path, registry lookup, `SSHPathSandbox`, realpath containment); the allow-list itself is `src/alfred/execution-plane/ssh/allowed-commands.ts`. Wiring real SSH into production (e.g. over Tailscale) is a separate design decision.

### Path aliases (tsconfig.json)
`@alfred/*`, `@ai/*`, `@voice/*`, `@data/*`, `@integrations/*`, `@core/*` all map to `src/*` subfolders. `apps/web/` has its own `tsconfig.json`, is a separate Next.js compilation unit, and **does not import from `src/` at all** (its tsconfig has no `src` aliases). With the Next.js route handlers gone, the only HTTP entry point for Alfred is `functions/index.js`, which pulls in selected `src/` modules through the functions bundle (see **Functions bundle**).

### Storage model — three tiers, one source of truth
1. **Git (`users/`)** — canonical authored baseline about Barış. Read-only at runtime, authoritative over vague inference.
2. **Firestore (`src/data/firestore/`)** — authoritative for conversation history (`conversations/{id}/messages/{id}`, atomic `sequence`) and long-term memory records (`memory_vectors/{id}`). If the vector store is wiped, it is rebuilt entirely from here via `npm run memory:reindex`.
3. **Vector store (`src/data/vector/`, `LocalFileVectorStore`)** — a purely rebuildable semantic search cache, never the source of truth.

Key distinctions to preserve when editing memory code:
- Conversation history (verbatim) ≠ long-term memory (durable facts/preferences only — chit-chat is discarded).
- Memory extraction runs on an isolated classification prompt (`src/ai/prompts/memory-extraction.ts`), completely separate from Alfred's conversational persona; assistant text is never attributed to the user. In production it runs on its own Groq model, `MEMORY_EXTRACTION_MODEL` (default `openai/gpt-oss-20b`), not the chat model: Groq free-plan limits are per model (gpt-oss-120b: 8,000 tokens/min), so sharing the chat model made every turn spend the chat budget twice. If Groq fails it falls back to Gemini `GEMINI_EXTRACTION_MODEL` (default `gemini-3.1-flash-lite`), then Ollama.
- `PrivacyFilter` (`src/alfred/cognitive/memory/privacy-filter.ts`) rejects candidate memories containing secrets (API keys, passwords, tokens) before persistence.
- Failure boundaries are intentionally non-cascading: embedding failure → no Firestore record; Firestore failure → no vector created; vector indexing failure → Firestore record kept with `indexStatus: "failed"` (re-indexable); extraction failure never affects the live chat response (it runs as a non-blocking background task).

### Streaming chat
The `api` function's `POST /chat` (`functions/index.js`) streams SSE frames `data: {json}\n\n` with `type` = `start` (`conversationId`, `provider`, `model`), `thinking`, `chunk` (`text`), `tool_call`, `tool_result`, `rate_limited` (`provider`, `waitMs`, `attempt`; only sent when the server really waits), `provider_fallback` (`from`, `to`, `model`, `reason`; see **Chat provider fallback**), `done`, `error` (`error`, plus `code` / `limitType` / `retryAfterMs` on rate-limit failures and `attemptedProviders` when every fallback failed). `start` names the first provider tried; the UI switches its model label and engine name on `provider_fallback`. `chunk` text can contain `<think>` traces; the client strips them before rendering. After `done` the server keeps the connection open until the memory write finishes, so the UI releases the composer on `done` rather than on stream close, and a per-turn guard keeps a late-closing stream from resetting a newer turn. `lib/sse.ts` drops unknown `type`s, so new event types are safe for old clients. `tests/unit/web-sse-parser.test.ts` pins the frame format.

**Groq rate limits (429).** The free plan caps `openai/gpt-oss-120b` at 8,000 tokens/minute and 200,000 tokens/day. The policy is `src/ai/providers/groq/rate-limit.ts` (bundled, pinned by `tests/unit/groq-rate-limit.test.ts`); only the body parsing is Groq-specific, the decision and message take a provider-neutral `RateLimitInfo`. `parseRateLimitInfo(retryAfterHeader, body)` returns the **real, unclamped** wait (a positive numeric `retry-after` header wins, else the body's "try again in …" hint: `3m19.152s`, `450ms`, `1m2.5s`, `2h5m`; else `null`) and `limitType` = `tpm` | `tpd` | `rpm` | `rpd` | `unknown` (from "(TPD)" / "tokens per day" etc.). `computeRateLimitWait({ info, attempt, spentMs })` decides **before sleeping**: give up at once on any daily limit (`daily_limit`), after 3 attempts per model call (`max_attempts`), or when the wait (real value, +0.6 s for a body hint, at least 2.5 s, 5 s without a hint) does not fit in what is left of the **25 s per-turn budget** across all calls and tool rounds (`budget_exhausted`); otherwise wait exactly that — waits are never clamped down, since waiting less than Groq asked only earns another 429. (On 24 Sep 2026 the old 2.5–15 s clamp slept 15 s twice on a TPD 429 that asked for 3m19s and then told the user "dakikalık … ~15 sn".) Only when it really waits does the server send `rate_limited` (`waitMs` = the actual sleep) and afterwards `thinking`; the UI replaces "Düşünüyor..." with a countdown ("Groq sınırına ulaşıldı, ~15 sn bekleniyor…"). When it gives up it throws `createRateLimitedError(detail, reason, info)` and the stream ends with `error` = `code: "rate_limited"`, `limitType`, `retryAfterMs` (the real value; omitted when unknown) and a short Turkish message from `rateLimitUserMessage(limitType, retryAfterMs)` via `toChatErrorEvent` (e.g. "Groq'un günlük token limiti doldu. Lütfen yaklaşık 3 dakika sonra tekrar deneyin.", "Groq'un dakikalık istek limiti doldu. Lütfen ~12 sn sonra tekrar deneyin.", fallback "Groq kullanım sınırına ulaşıldı. Lütfen biraz sonra tekrar deneyin."; `formatTurkishDuration`: `~N sn` under a minute, then rounded `yaklaşık N dakika` / `N saat M dakika`). The raw Groq body only reaches the logs (`llm_rate_limited` with `limit_type`, `retry_after_ms` (real), `decision` = `wait` | `give_up`, `wait_ms` (the sleep taken, 0 on give-up), `attempt`, `round`, `total_wait_ms`, `budget_ms`, `outcome` = `retry` | `daily_limit` | `max_attempts` | `budget_exhausted`, and a truncated `detail`; `llm_request` carries `rate_limit_retries`, `rate_limit_wait_ms` and, on failure, `error_code` / `rate_limit_reason` / `rate_limit_type`). The memory-extraction Groq call never waits (it runs after the reply and falls back to Ollama); on a 429 its `memory_extraction_provider_error` log adds `limit_type`, `retry_after_ms` and `decision: "give_up"`. Other errors keep sending `err.message` as before. Since the chat fallback, this 429 loop runs per provider inside `src/ai/providers/chat-fallback/chat-turn.ts` (same budget across all providers of the turn); `createRateLimitedError(…, providerLabel)` / `rateLimitUserMessage(…, providerLabel)` name a non-Groq provider ("Cerebras'ın dakikalık istek limiti doldu…"), the Groq default output is unchanged.

**Chat provider fallback.** The default order is **Groq → Gemini → OpenRouter** (`DEFAULT_CHAT_PROVIDER_ORDER`). Cerebras is configured but left out of it since 24 Sep 2026: the account answers every request with 402 `payment_required`, so its steps only added two failed calls and two ERROR logs; add `"cerebras", "cerebras_secondary"` back before `"openrouter"` in `DEFAULT_CHAT_PROVIDER_ORDER` once its billing is set up (the key binding and tests are still in place). With every provider listed, `/chat` moves on in this order when the primary is unavailable: **Groq** `openai/gpt-oss-120b` (`GROQ_MODEL`) → **Gemini** `gemini-3.8-flash` (`GEMINI_CHAT_MODEL`; OpenAI-compatible endpoint `generativelanguage.googleapis.com/v1beta/openai/chat/completions`, `reasoning_effort: "low"`, `max_tokens` 4096, `stream_options.include_usage`) → **Cerebras** `gpt-oss-120b` (`CEREBRAS_MODEL`; free tier 5 requests/min, so a 429 here moves on without waiting, `waitOnRateLimit: false`) → **Cerebras** `qwen-3.8-27b` (`CEREBRAS_SECONDARY_MODEL`, `none` skips it; `reasoning_effort: "low"`) → **OpenRouter** `openai/gpt-oss-120b` (`OPENROUTER_MODEL`; paid model, needs credits — `qwen/qwen3.8-27b:free` is a free tool-capable alternative; sends `HTTP-Referer` / `X-Title` / `X-OpenRouter-Title` and `provider.require_parameters: true`). `CHAT_FALLBACK_ORDER` (comma-separated ids) reorders or trims the chain (`groq` alone disables it). All pure, bundled modules in `src/ai/providers/chat-fallback/`:
- `chat-providers.ts` — provider table, `isUsableApiKey` (empty / `unset` / `none` = unconfigured, the step is skipped), `resolveChatProviders`, and `buildChatRequestBody` / `buildChatRequestHeaders`. **Groq's request is byte-for-byte the former payload** (`{ model, messages, stream, temperature: 0.6, max_tokens: 1500, tools? }`, same headers); `tests/unit/chat-fallback-providers.test.ts` compares the JSON string.
- `openai-stream.ts` — one SSE parser for all four: tool-call fragments keyed by `index`, else `id` (Gemini sends whole calls with `id` and no `index`), Gemini's `extra_content.google.thought_signature` kept and echoed back with the call (Gemini 3 answers 400 without it), last `usage` / `x_groq.usage` wins (counted once), `delta.reasoning` ignored, `:` comment lines (OpenRouter) skipped, in-stream `{"error": …}` recorded. Fixtures per provider: `tests/unit/fixtures/chat-provider-streams.ts`.
- `failover.ts` — `classifyChatFailure` + `decideFailover`: move on for a 429 that cannot be waited within the turn budget (incl. any daily limit), 5xx, network errors, timeouts, an in-stream error, and any other 4xx (logged at ERROR: key/model/request problem) — **only while no `chunk` has been sent in this turn**; with partial text on screen the turn fails as before (partial text saved as `interrupted`). An empty answer (`empty_response`) and unrecognised errors never move on. When every provider failed, the error is the first rate-limit error (else the last) and `toChatTurnErrorEvent` appends "Yedek sağlayıcılar da yanıt veremedi."; a Groq-only turn gets exactly the old `toChatErrorEvent` event.
- `chat-turn.ts` — `runChatTurnWithFallback`: the former Groq tool loop (tools on every round except the last of `MAX_TURNS` = 3, `get_current_time` via the injected `runTool`, `llm_stream_error`, the shared 429 policy), run per provider with fetch/SSE/sleep/logs injected. On failover **the whole turn restarts from the user's message** on the next provider, with the system prompt rebuilt for it (`buildMessages` → `buildAlfredSystemPrompt({ runtime: { provider, model } })`; the capability line then reads e.g. "reasoning via Google Gemini (gemini-3.8-flash), standing in because Groq is unavailable"). Tool rounds are not carried over because tool history is provider-specific (Gemini rejects prior calls without its thought signature; ids differ); the tool is cheap and deterministic. `tests/unit/chat-fallback-turn.test.ts` drives the whole turn on mocked fetch.
- Logs: `llm_request` has `provider` / `model` (the provider that answered or failed last), `fallback_from` (list), `attempted_providers` (list) and `skipped_providers` (no usable key); each switch logs `llm_provider_fallback` (`from`, `from_model`, `to`, `to_model`, `reason`, `http_status`, truncated `error`). Keys are never logged (a test checks it).
- `extraction-providers.ts` — memory extraction: Groq `MEMORY_EXTRACTION_MODEL` → Gemini `GEMINI_EXTRACTION_MODEL` (default `gemini-3.1-flash-lite`, `reasoning_effort: "minimal"`, no `response_format`) → the existing Ollama step in `functions/index.js`. Never waits on a 429.
- The Ollama path (`ALFRED_LLM_PROVIDER=ollama`) is unchanged and has no fallback.

### Auth — single-user, Google only
The app is locked to one person. There is no sign-up, no password login and no SMS MFA (all removed in Sep 2026).

- **Google Sign-In only**, popup with an automatic fallback to redirect on `auth/internal-error`, `auth/popup-blocked` or `auth/cancelled-popup-request` (`apps/web/lib/auth.ts`).
- **UID allow-list**: any account whose `uid` is not the single allowed value is signed straight back out with `auth/unauthorized-uid` (popup, redirect result, and restored sessions via `subscribeAuthState`). The UID has exactly one definition per runtime:
  - **Web app** — `apps/web/lib/allowed-uid.ts` (`process.env.NEXT_PUBLIC_ALLOWED_UID || literal`; the `NEXT_PUBLIC_` value is inlined at build time, so it works in the static export), imported and re-exported by `apps/web/lib/auth.ts`.
  - **Cloud Functions** — `functions/index.js` (`process.env.ALLOWED_UID || literal`).

  Changing the UID therefore means editing those two places (or setting the env vars). The UID is not a secret; the client-side check is UX only, and real enforcement is server-side in `functions/index.js` (ID token + App Check).
- **App Check** (reCAPTCHA Enterprise) is **enforced**: initialised in `apps/web/lib/firebase.ts` (`getAppCheckToken()` feeds the `X-Firebase-AppCheck` header on every `apiFetch`), verified server-side in `functions/index.js` alongside the Firebase ID token. A missing or invalid token returns 401 with a Turkish message and `code: "app_check_missing"` / `"app_check_invalid"` (logged as `event: "app_check"`); only `/health` and `/` are exempt. `alfredCallable` uses `enforceAppCheck` with the same flag. Enforcement is on by default (switched on 24 Sep 2026 after production traffic logged `app_check: "valid"`), off in the emulator (`FUNCTIONS_EMULATOR`), and `ENFORCE_APP_CHECK=false` disables it. Local `npm run dev:web` against the production API needs the App Check debug token registered in the Firebase console, or requests get 401.
- **Server-side enforcement is what actually protects the data.** `functions/index.js` `api` rejects every request except `/` and `/health` without a valid Firebase ID token (401) or with a UID other than `ALLOWED_UID` (403). The user is always the token's UID; a client-supplied `userId` that differs is rejected, and a conversation owned by another `userId` returns 404. `alfredCallable` checks `request.auth.uid` the same way. The web app therefore mounts the chat UI (and loads conversations) only after Firebase has restored an allowed session, and `apiFetch` refuses authenticated calls without a signed-in user.
- `tests/unit/uid-whitelist.test.ts` (against a mocked Firebase Auth), `tests/unit/auth-error-messages.test.ts` and `tests/unit/web-api-client.test.ts` pin this behaviour — they will fail if the UID, the error contract or the auth headers change.

### Deployment — Firebase Hosting + Cloud Functions only
- `firebase.json` — Firestore rules/indexes, the `functions` codebase, and Hosting. Hosting serves `apps/web/out` (the Next.js static export — it must be built first), rewrites `/api/**` to the `api` function and everything else to `index.html`. `Cache-Control` is `no-cache` everywhere except the content-hashed `/_next/static/**`, which is cached for a year (the later, more specific header rule wins).
- There is no App Hosting and no server runtime for the web app (`apphosting.yaml` was removed). Production is the static export on Hosting plus the `api` / `alfredCallable` functions.
- **CI**: `.github/workflows/ci.yml` runs `npm ci`, `npm run lint`, `npm run typecheck`, `npm run typecheck:tests`, `npm run test:unit`, the functions bundle build/check, the `apps/web` typecheck and `npm run build:web` on every pull request (Node 22, no `.env`). `.github/workflows/deploy.yml` reuses it as a `test` job, then runs `npm ci`, `npm run build:web`, the functions bundle build and `firebase deploy --only hosting,functions,firestore:rules,firestore:indexes`, on any push to `main` touching `apps/**`, `src/**`, `functions/**`, `firebase.json`, `.firebaserc`, `firestore.rules`, `firestore.indexes.json`, `package.json`, `package-lock.json` or either workflow. A lint error, red typecheck, unit test or web build therefore blocks the deploy.

### Functions bundle — `functions/` imports `src/` via esbuild
`functions/index.js` is the **source**, not what runs. `functions/build.js` bundles it with esbuild (ESM, `platform: node`, `target: node22`, `packages: "external"`) into `functions/lib/index.js`, which `functions/package.json` `"main"` points at. `functions/lib/` is gitignored and must be built before `firebase deploy` or the emulator: `firebase.json` runs `npm --prefix "$RESOURCE_DIR" run build` as the functions `predeploy` hook, and `deploy.yml` also builds explicitly. Only `functions/` is uploaded, so the bundle must be self-contained apart from npm packages.

- Import shared code with **relative paths** to the `.js` specifier of the `.ts` file (`import { x } from "../src/data/vector/cosine-similarity.js"`), same as inside `src/`. esbuild strips types; `npm run typecheck` is what type-checks `src/`.
- npm dependencies are **not** bundled. `build.js` fails if the bundle imports a package that is not in `functions/package.json` `dependencies`, or if it stops exporting `api` / `alfredCallable`. A `src/` module that needs a new package means adding it to `functions/package.json` too.
- Only migrate pure modules. Nothing bundled may read files at import time (e.g. `UserProfileLoader` reading `users/*.md` would break: those files are not uploaded — the bundle gets them through `user-profile.generated.ts` instead, and `build.js` fails if that module drops out of the bundle) or pull in `src/core/config`, whose modules import `dotenv` (a root-only dependency, so the build check rejects it) and call `dotenv.config()` at import time.
- `"gcp-build": ""` in `functions/package.json` is deliberate: Cloud Build would otherwise run the `build` script in the cloud, where `../src` does not exist. Don't remove it.

### Secrets — LLM keys live only in Secret Manager
`GROQ_API_KEY`, `GEMINI_API_KEY`, `CEREBRAS_API_KEY` and `OPENROUTER_API_KEY` are never taken from the caller. There is no request-header path, and the browser neither stores nor sends keys.
- `functions/index.js` binds all four through `defineSecret()` (Cerebras and OpenRouter only on `api`; `alfredCallable` needs no LLM key). Because they are bound, **a deploy fails if a secret does not exist**; create a missing one first, with the placeholder value `unset` if there is no key yet (the fallback then skips that provider):

  ```bash
  firebase functions:secrets:set CEREBRAS_API_KEY     # paste the key, or: unset
  firebase functions:secrets:set OPENROUTER_API_KEY   # paste the key, or: unset
  firebase functions:secrets:access CEREBRAS_API_KEY  # check (prints the value; don't paste it anywhere)
  ```
-  `gizliOku()` falls back to `process.env` only when the secret isn't bound, e.g. in tests. The emulator reads `functions/.secret.local`, which is gitignored.
- `src/` and the local Next.js app read `process.env`, filled from `.env`.

`defineSecret` requires names that are valid environment variables, so the names are `GROQ_API_KEY` / `GEMINI_API_KEY` / `CEREBRAS_API_KEY` / `OPENROUTER_API_KEY` (not `groq-api-key`). All four exist in `butler-alfred` (Cerebras and OpenRouter since 24 Sep 2026). The CI deploy identity is `firebase-adminsdk-fbsvc@butler-alfred.iam.gserviceaccount.com`, and it has **Secret Manager Admin**. Admin, not just accessor, because the deploy grants the runtime service account access to each secret.

**Do not put any of these keys in `functions/.env`.** The Firebase CLI deploys that file as plain env vars. Cloud Run then rejects the update with `Secret environment variable overlaps non secret environment variable`, which is exactly how the `api` function got stuck after an earlier manual deploy. If that error appears, remove the plain variable from the `api` Cloud Run service (console → Cloud Run → `api` → Edit → Variables & Secrets) and redeploy. Do not "fix" it by reverting to plain `process.env`.
