# Production internals — B.U.T.L.E.R. Alfred

Detailed reference for how the production path (`functions/index.js` plus the `src/` modules bundled into it) behaves: the SSE contract, rate limits, provider fallback, auth, deployment, the functions bundle and every module it shares with `src/`, and secrets. `CLAUDE.md` keeps the rules and points here; `docs/ARCHITECTURE.md` covers structure and invariants; `docs/OPERATIONS.md` covers alerting and the runbook.

Much of this is pinned by tests: when a test named here fails after a change, this document says what the test protects.

## Canonical user profile digest (`users/`)

`users/` — canonical, git-versioned, **read-only-at-runtime** profile of Barış (`USER_PROFILE.md`, `PREFERENCES.md`, `WORKING_STYLE.md`). Never written to by the running app. **The prompt carries a reviewed digest of these files, not the files themselves.** Rendered verbatim they cost ~2,000 tokens a turn, most of it repeating the persona, so the prompt's `CANONICAL USER PROFILE` block is `src/alfred/cognitive/context/user-profile.digest.md`: a hand-written condensation (~620 tokens) that keeps the facts and rules that change answers. Its header records the sha256 of each `users/*.md` it was written from. `scripts/generate-user-profile-sources.mjs` embeds the files (`USER_PROFILE_SOURCES`) and the digest body (`USER_PROFILE_DIGEST`) in the committed `user-profile.generated.ts` (nothing reads files at runtime in the bundle). Editing `users/*.md` therefore needs a digest update before it can ship: `npm run generate:user-profile`, `tests/unit/user-profile-renderer.test.ts`, `tests/unit/functions-system-prompt.test.ts` and `functions/build.js` all fail until the digest's hashes match, and the script prints the new hash lines. Update the digest text to reflect the edit, paste the hashes, and refresh the prompt fixture (see **Commands** in `CLAUDE.md`). In src/, `ContextBuilder.formatUserProfileBlock()` uses the digest when the loaded files are the committed ones; any other sources (e.g. a test directory) are rendered verbatim by `renderUserProfileBlock()` (`user-profile-renderer.ts`), so a different profile is never silently swapped for the digest.

## SSH in production

**Production does not use any of it, and offers no SSH tools.** There is no SSH connection behind `functions/index.js`: the ssh_* tools used to return canned results (a fixed 15-entry `Belgeler/` listing and fixed `df`/`pwd`/`whoami`/`uname` output) that Alfred presented as real server state. They were removed from the tool list: production sends only `get_current_time`, an unexpected `ssh_*` call gets `Tool … not recognized.`, and the persona (built with `sshAvailable: false`, the default) says server access is not connected and forbids inventing server state. `buildAlfredSystemPrompt({ sshAvailable: true })` restores the SSH instructions byte-for-byte for a caller that really executes them. The three tool definitions and argument rules (default host `home-server`, default path `Belgeler`, exact-match allow-list, path deny-list) remain in `src/ai/tools/ssh/ssh-tool-definitions.ts` for the src tools, which add the real-SSH guards (non-string host/path, registry lookup, `SSHPathSandbox`, realpath containment); the allow-list itself is `src/alfred/execution-plane/ssh/allowed-commands.ts`. Wiring real SSH into production (e.g. over Tailscale) is a separate design decision.

## Streaming chat (SSE)

The `api` function's `POST /chat` (`functions/index.js`) streams SSE frames `data: {json}\n\n` with `type` = `start` (`conversationId`, `provider`, `model`), `thinking`, `chunk` (`text`), `tool_call`, `tool_result`, `rate_limited` (`provider`, `waitMs`, `attempt`; only sent when the server really waits), `provider_fallback` (`from`, `to`, `model`, `reason`; see **Chat provider fallback**), `done`, `error` (`error`, plus `code` / `limitType` / `retryAfterMs` on rate-limit failures and `attemptedProviders` when every fallback failed). `start` names the first provider tried; the UI switches its model label and engine name on `provider_fallback`. `chunk` text can contain `<think>` traces; the client strips them before rendering. After `done` the server keeps the connection open until the memory write finishes, so the UI releases the composer on `done` rather than on stream close, and a per-turn guard keeps a late-closing stream from resetting a newer turn. `lib/sse.ts` drops unknown `type`s, so new event types are safe for old clients. `tests/unit/web-sse-parser.test.ts` pins the frame format.

## Groq rate limits (429)

The free plan caps `openai/gpt-oss-120b` at 8,000 tokens/minute and 200,000 tokens/day. The policy is `src/ai/providers/groq/rate-limit.ts` (bundled, pinned by `tests/unit/groq-rate-limit.test.ts`); only the body parsing is Groq-specific, the decision and message take a provider-neutral `RateLimitInfo`. `parseRateLimitInfo(retryAfterHeader, body)` returns the **real, unclamped** wait (a positive numeric `retry-after` header wins, else the body's "try again in …" hint: `3m19.152s`, `450ms`, `1m2.5s`, `2h5m`; else `null`) and `limitType` = `tpm` | `tpd` | `rpm` | `rpd` | `unknown` (from "(TPD)" / "tokens per day" etc.). `computeRateLimitWait({ info, attempt, spentMs })` decides **before sleeping**: give up at once on any daily limit (`daily_limit`), after 3 attempts per model call (`max_attempts`), or when the wait (real value, +0.6 s for a body hint, at least 2.5 s, 5 s without a hint) does not fit in what is left of the **25 s per-turn budget** across all calls and tool rounds (`budget_exhausted`); otherwise wait exactly that — waits are never clamped down, since waiting less than Groq asked only earns another 429. (On 24 Sep 2026 the old 2.5–15 s clamp slept 15 s twice on a TPD 429 that asked for 3m19s and then told the user "dakikalık … ~15 sn".) Only when it really waits does the server send `rate_limited` (`waitMs` = the actual sleep) and afterwards `thinking`; the UI replaces "Düşünüyor..." with a countdown ("Groq sınırına ulaşıldı, ~15 sn bekleniyor…"). When it gives up it throws `createRateLimitedError(detail, reason, info)` and the stream ends with `error` = `code: "rate_limited"`, `limitType`, `retryAfterMs` (the real value; omitted when unknown) and a short Turkish message from `rateLimitUserMessage(limitType, retryAfterMs)` via `toChatErrorEvent` (e.g. "Groq'un günlük token limiti doldu. Lütfen yaklaşık 3 dakika sonra tekrar deneyin.", "Groq'un dakikalık istek limiti doldu. Lütfen ~12 sn sonra tekrar deneyin.", fallback "Groq kullanım sınırına ulaşıldı. Lütfen biraz sonra tekrar deneyin."; `formatTurkishDuration`: `~N sn` under a minute, then rounded `yaklaşık N dakika` / `N saat M dakika`). The raw Groq body only reaches the logs (`llm_rate_limited` with `limit_type`, `retry_after_ms` (real), `decision` = `wait` | `give_up`, `wait_ms` (the sleep taken, 0 on give-up), `attempt`, `round`, `total_wait_ms`, `budget_ms`, `outcome` = `retry` | `daily_limit` | `max_attempts` | `budget_exhausted`, and a truncated `detail`; `llm_request` carries `rate_limit_retries`, `rate_limit_wait_ms` and, on failure, `error_code` / `rate_limit_reason` / `rate_limit_type`). The memory-extraction Groq call never waits (it runs after the reply and falls back to Ollama); on a 429 its `memory_extraction_provider_error` log adds `limit_type`, `retry_after_ms` and `decision: "give_up"`. Other errors keep sending `err.message` as before. Since the chat fallback, this 429 loop runs per provider inside `src/ai/providers/chat-fallback/chat-turn.ts` (same budget across all providers of the turn); `createRateLimitedError(…, providerLabel)` / `rateLimitUserMessage(…, providerLabel)` name a non-Groq provider ("Cerebras'ın dakikalık istek limiti doldu…"), the Groq default output is unchanged.

## Chat provider fallback

The default order is **Groq → Gemini → OpenRouter** (`DEFAULT_CHAT_PROVIDER_ORDER`). Cerebras is configured but left out of it since 24 Sep 2026: the account answers every request with 402 `payment_required`, so its steps only added two failed calls and two ERROR logs; add `"cerebras", "cerebras_secondary"` back before `"openrouter"` in `DEFAULT_CHAT_PROVIDER_ORDER` once its billing is set up (the key binding and tests are still in place). With every provider listed, `/chat` moves on in this order when the primary is unavailable: **Groq** `openai/gpt-oss-120b` (`GROQ_MODEL`) → **Gemini** `gemini-3.8-flash` (`GEMINI_CHAT_MODEL`; OpenAI-compatible endpoint `generativelanguage.googleapis.com/v1beta/openai/chat/completions`, `reasoning_effort: "low"`, `max_tokens` 4096, `stream_options.include_usage`) → **Cerebras** `gpt-oss-120b` (`CEREBRAS_MODEL`; free tier 5 requests/min, so a 429 here moves on without waiting, `waitOnRateLimit: false`) → **Cerebras** `qwen-3.8-27b` (`CEREBRAS_SECONDARY_MODEL`, `none` skips it; `reasoning_effort: "low"`) → **OpenRouter** `openai/gpt-oss-120b` (`OPENROUTER_MODEL`; paid model, needs credits — `qwen/qwen3.8-27b:free` is a free tool-capable alternative; sends `HTTP-Referer` / `X-Title` / `X-OpenRouter-Title` and `provider.require_parameters: true`). `CHAT_FALLBACK_ORDER` (comma-separated ids) reorders or trims the chain (`groq` alone disables it). All pure, bundled modules in `src/ai/providers/chat-fallback/`:
- `chat-providers.ts` — provider table, `isUsableApiKey` (empty / `unset` / `none` = unconfigured, the step is skipped), `resolveChatProviders`, and `buildChatRequestBody` / `buildChatRequestHeaders`. **Groq's request is byte-for-byte the former payload** (`{ model, messages, stream, temperature: 0.6, max_tokens: 1500, tools? }`, same headers); `tests/unit/chat-fallback-providers.test.ts` compares the JSON string.
- `openai-stream.ts` — one SSE parser for all four: tool-call fragments keyed by `index`, else `id` (Gemini sends whole calls with `id` and no `index`), Gemini's `extra_content.google.thought_signature` kept and echoed back with the call (Gemini 3 answers 400 without it), last `usage` / `x_groq.usage` wins (counted once), `delta.reasoning` ignored, `:` comment lines (OpenRouter) skipped, in-stream `{"error": …}` recorded. Fixtures per provider: `tests/unit/fixtures/chat-provider-streams.ts`.
- `failover.ts` — `classifyChatFailure` + `decideFailover`: move on for a 429 that cannot be waited within the turn budget (incl. any daily limit), 5xx, network errors, timeouts, an in-stream error, and any other 4xx (logged at ERROR: key/model/request problem) — **only while no `chunk` has been sent in this turn**; with partial text on screen the turn fails as before (partial text saved as `interrupted`). An empty answer (`empty_response`) and unrecognised errors never move on. When every provider failed, the error is the first rate-limit error (else the last) and `toChatTurnErrorEvent` appends "Yedek sağlayıcılar da yanıt veremedi."; a Groq-only turn gets exactly the old `toChatErrorEvent` event.
- `chat-turn.ts` — `runChatTurnWithFallback`: the former Groq tool loop (tools on every round except the last of `MAX_TURNS` = 3, `get_current_time` via the injected `runTool`, `llm_stream_error`, the shared 429 policy), run per provider with fetch/SSE/sleep/logs injected. On failover **the whole turn restarts from the user's message** on the next provider, with the system prompt rebuilt for it (`buildMessages` → `buildAlfredSystemPrompt({ runtime: { provider, model } })`; the capability line then reads e.g. "reasoning via Google Gemini (gemini-3.8-flash), standing in because Groq is unavailable"). Tool rounds are not carried over because tool history is provider-specific (Gemini rejects prior calls without its thought signature; ids differ); the tool is cheap and deterministic. `tests/unit/chat-fallback-turn.test.ts` drives the whole turn on mocked fetch.
- Logs: `llm_request` has `provider` / `model` (the provider that answered or failed last), `fallback_from` (list), `attempted_providers` (list) and `skipped_providers` (no usable key); each switch logs `llm_provider_fallback` (`from`, `from_model`, `to`, `to_model`, `reason`, `http_status`, truncated `error`). Keys are never logged (a test checks it).
- `extraction-providers.ts` — memory extraction: Groq `MEMORY_EXTRACTION_MODEL` → Gemini `GEMINI_EXTRACTION_MODEL` (default `gemini-3.1-flash-lite`, `reasoning_effort: "minimal"`, no `response_format`) → Ollama `/api/chat` (`ollamaUrl` unless empty or containing "placeholder", 30 s; only a thrown error is reported, an HTTP error or empty answer is silent, as the former inline step was). Never waits on a 429. Used by production (`functions/memory-extraction.js`) and src's `MemoryExtractor` alike.
- The Ollama path (`ALFRED_LLM_PROVIDER=ollama`) is unchanged and has no fallback.

## Auth — single-user, Google only

The app is locked to one person. There is no sign-up, no password login and no SMS MFA (all removed in Sep 2026).

- **Google Sign-In only**, popup with an automatic fallback to redirect on `auth/internal-error`, `auth/popup-blocked` or `auth/cancelled-popup-request` (`apps/web/lib/auth.ts`).
- **UID allow-list**: any account whose `uid` is not the single allowed value is signed straight back out with `auth/unauthorized-uid` (popup, redirect result, and restored sessions via `subscribeAuthState`). The UID has exactly one definition per runtime:
  - **Web app** — `apps/web/lib/allowed-uid.ts` (`process.env.NEXT_PUBLIC_ALLOWED_UID || literal`; the `NEXT_PUBLIC_` value is inlined at build time, so it works in the static export), imported and re-exported by `apps/web/lib/auth.ts`.
  - **Cloud Functions** — `functions/index.js` (`process.env.ALLOWED_UID || literal`).

  Changing the UID therefore means editing those two places (or setting the env vars). The UID is not a secret; the client-side check is UX only, and real enforcement is server-side in `functions/index.js` (ID token + App Check).
- **App Check** (reCAPTCHA Enterprise) is **enforced**: initialised in `apps/web/lib/firebase.ts` (`getAppCheckToken()` feeds the `X-Firebase-AppCheck` header on every `apiFetch`), verified server-side in `functions/index.js` alongside the Firebase ID token. A missing or invalid token returns 401 with a Turkish message and `code: "app_check_missing"` / `"app_check_invalid"` (logged as `event: "app_check"`); only `/health` and `/` are exempt. `alfredCallable` uses `enforceAppCheck` with the same flag. Enforcement is on by default (switched on 24 Sep 2026 after production traffic logged `app_check: "valid"`), off in the emulator (`FUNCTIONS_EMULATOR`), and `ENFORCE_APP_CHECK=false` disables it. Local `npm run dev:web` against the production API needs the App Check debug token registered in the Firebase console, or requests get 401.
- **Server-side enforcement is what actually protects the data.** `functions/index.js` `api` rejects every request except `/` and `/health` without a valid Firebase ID token (401) or with a UID other than `ALLOWED_UID` (403). The user is always the token's UID; a client-supplied `userId` that differs is rejected, and a conversation owned by another `userId` returns 404. `alfredCallable` checks `request.auth.uid` the same way. The web app therefore mounts the chat UI (and loads conversations) only after Firebase has restored an allowed session, and `apiFetch` refuses authenticated calls without a signed-in user.
- `tests/unit/uid-whitelist.test.ts` (against a mocked Firebase Auth), `tests/unit/auth-error-messages.test.ts` and `tests/unit/web-api-client.test.ts` pin this behaviour — they will fail if the UID, the error contract or the auth headers change.

## Deployment — Firebase Hosting + Cloud Functions only

- `firebase.json` — Firestore rules/indexes, the `functions` codebase, and Hosting. Hosting serves `apps/web/out` (the Next.js static export — it must be built first), rewrites `/api/**` to the `api` function and everything else to `index.html`. `Cache-Control` is `no-cache` everywhere except the content-hashed `/_next/static/**`, which is cached for a year (the later, more specific header rule wins).
- There is no App Hosting and no server runtime for the web app (`apphosting.yaml` was removed). Production is the static export on Hosting plus the `api` / `alfredCallable` functions.
- **CI**: `.github/workflows/ci.yml` runs `npm ci`, `npm run lint`, `npm run typecheck`, `npm run typecheck:tests`, `npm run test:unit`, `npm run test:integration:offline` (no secrets, no network: only the local checks run, everything needing a service is reported as skipped), the functions bundle build/check, the `apps/web` typecheck and `npm run build:web` on every pull request (Node 22, no `.env`). `.github/workflows/deploy.yml` reuses it as a `test` job, then runs `npm ci`, `npm run build:web`, the functions bundle build and `firebase deploy --only hosting,functions,firestore:rules,firestore:indexes`, on any push to `main` touching `apps/**`, `src/**`, `functions/**`, `firebase.json`, `.firebaserc`, `firestore.rules`, `firestore.indexes.json`, `package.json`, `package-lock.json` or either workflow. A lint error, red typecheck, unit or offline integration test or web build therefore blocks the deploy.
- **Rollback**: `firebase hosting:rollback` (or Hosting → Release history → Roll back in the console) restores the previous Hosting release without a rebuild.
- **Deploy failure notification**: GitHub emails the user who triggered a failed workflow run (for `deploy.yml`, whoever merged to `main`); with one owner that is enough, so the workflows have no notification step and need no extra secret. The `Alfred: Cloud Functions deploy failed` alert (see **Alerting**) also covers manual `firebase deploy`s.

## Alerting

`docs/OPERATIONS.md` is the reference (alert list, thresholds, cost, Turkish runbook). `scripts/monitoring/setup-alerts.sh` (bash + GA `gcloud`, `jq`, `curl`; dry-run unless `--apply`, idempotent) creates an email notification channel (over the Monitoring REST API, since `gcloud monitoring channels` is alpha/beta only), the log-based counter metrics in `scripts/monitoring/metrics/*.json` (file name = metric name) and the alert policies in `scripts/monitoring/policies/*.json` (the script injects the channel; everything carries `managed_by=alfred-setup-alerts`, which `teardown-alerts.sh` uses). Policies: CRITICAL on any final chat failure (`llm_request` `outcome=error`, i.e. the fallback chain is exhausted), ≥ 3 5xx in 5 min (Cloud Run's built-in `request_count`) and any container startup failure; ERROR on ≥ 5 App Check rejections in 10 min and any failed Cloud Functions deploy (activity audit log); WARNING on ≥ 3 provider fallbacks / 10 min, ≥ 3 stream errors, rate-limit give-ups or embedding errors / 30 min, ≥ 3 memory-extraction failures / 1 h. All auto-close. **The metrics filter on log event names and fields** (`event`, `outcome`, `exempt`); `tests/unit/monitoring-config.test.ts` fails if a filtered event or outcome value disappears from `functions/index.js` / `chat-turn.ts`, so when renaming a log event or field, update the metric JSON and re-run the setup script. The owner applies it; nothing in CI or the deploy touches Monitoring.

## Functions bundle — `functions/` imports `src/` via esbuild

`functions/index.js` is the **source**, not what runs. `functions/build.js` bundles it with esbuild (ESM, `platform: node`, `target: node22`, `packages: "external"`) into `functions/lib/index.js`, which `functions/package.json` `"main"` points at. `functions/lib/` is gitignored and must be built before `firebase deploy` or the emulator: `firebase.json` runs `npm --prefix "$RESOURCE_DIR" run build` as the functions `predeploy` hook, and `deploy.yml` also builds explicitly. Only `functions/` is uploaded, so the bundle must be self-contained apart from npm packages.

- Import shared code with **relative paths** to the `.js` specifier of the `.ts` file (`import { x } from "../src/data/vector/cosine-similarity.js"`), same as inside `src/`. esbuild strips types; `npm run typecheck` is what type-checks `src/`.
- npm dependencies are **not** bundled. `build.js` fails if the bundle imports a package that is not in `functions/package.json` `dependencies`, or if it stops exporting `api` / `alfredCallable`. A `src/` module that needs a new package means adding it to `functions/package.json` too.
- Only migrate pure modules. Nothing bundled may read files at import time (e.g. `UserProfileLoader` reading `users/*.md` would break: those files are not uploaded — the bundle gets them through `user-profile.generated.ts` instead, and `build.js` fails if that module drops out of the bundle) or pull in `src/core/config`, whose modules import `dotenv` (a root-only dependency, so the build check rejects it) and call `dotenv.config()` at import time.
- `"gcp-build": ""` in `functions/package.json` is deliberate: Cloud Build would otherwise run the `build` script in the cloud, where `../src` does not exist. Don't remove it.
- **Shared so far** (anything changed here ships to production):

  - from `src/ai/prompts/memory-extraction.ts` the extraction system prompt (`buildMemoryExtractionSystemPrompt`), `buildMemoryExtractionUserPrompt`, `extractJsonPayload` and the candidate validation (`getMemoryExtractionCandidates` + `validateMemoryCandidate`, which never throws: a non-object entry (e.g. `null`) is skipped and the rest of the list still runs; trimmed content >= 5 chars; confidence must be a finite number or plain decimal string in [0, 1] and >= 0.70, anything else, including a missing value, is rejected; `action` is create/forget/supersede matched case-insensitively after trimming, anything else becomes `"create"` so the duplicate check applies; `memoryType` must be one of the prompt's types, anything else becomes `"general"`. The prompt no longer asks for `targetMemoryHint`, which production never read. `parseMemoryExtractionResponse` and `DEFAULT_EXTRACTION_MIN_CONFIDENCE` follow the same rules, so src and production accept identical candidates. Production's `extractAndPersistMemories` now lives in `functions/memory-extraction.js` (`createExtractAndPersistMemories`, deps injected by `index.js`) and calls `callMemoryExtractionProviders` (Groq → Gemini → Ollama); a skipped turn logs `memory_extraction` `outcome: "nothing"` with `skip_reason`. src's `MemoryExtractor` runs the same pipeline and, by default, the same chain (`defaultExtractionCaller`: `GROQ_API_KEY` + `MEMORY_EXTRACTION_MODEL`, `GEMINI_API_KEY` + `GEMINI_EXTRACTION_MODEL`, `OLLAMA_BASE_URL` / `OLLAMA_MODEL`; `provider` or `call` options override it), with `MEMORY_EXTRACTION_BUDGET_MS` (10 s) as its default timeout. Two production changes came with it, both pinned: the short-circuit (src's rule; the prompt already demanded `shouldRemember: false` for those messages, so it only saves a call) and an Ollama answer with non-string content counting as no answer (it used to throw in `extractJsonPayload`). `tests/unit/memory-extraction-pipeline.test.ts` runs an 8,000-turn differential against a verbatim copy of the former code (`tests/unit/fixtures/legacy-extract-and-persist.js`, do not edit): identical fetches, timeouts, logs, persist calls and results on every other turn, plus a 3,000-turn test that `MemoryExtractor` sends the same requests and accepts the same candidates as production.
- **Still different, on purpose: the storage layer only.** Production keeps the vector inside the Firestore record, so it writes the finished record as `indexed` and commits a supersede (old record `superseded` + new record) in one Firestore batch. `MemoryService` writes through `IMemoryRepository` (`pending` → `indexed` / `failed`) and then indexes into a separate, rebuildable vector store; the two can't share a transaction, so on supersede it writes (and indexes) the new record first and marks the old one afterwards (a failure in between leaves a recoverable duplicate, never a lost fact). Both are storage ports of the same `runMemoryWriteLoop`. Also runtime-only: production's 10 s budget covers extraction *and* persistence (Cloud Run throttles CPU after the response), `MemoryExtractor`'s timeout covers the model call alone.
- CI (`ci.yml`, same `Typecheck & Unit Tests` job) installs `functions/` deps, builds the bundle and runs `check:bundle`, so a broken bundle blocks the deploy.

## Secrets — LLM keys live only in Secret Manager

`GROQ_API_KEY`, `GEMINI_API_KEY`, `CEREBRAS_API_KEY` and `OPENROUTER_API_KEY` are never taken from the caller. There is no request-header path, and the browser neither stores nor sends keys.
- `functions/index.js` binds all four through `defineSecret()` (Cerebras and OpenRouter only on `api`; `alfredCallable` needs no LLM key). Because they are bound, **a deploy fails if a secret does not exist**; create a missing one first, with the placeholder value `unset` if there is no key yet (the fallback then skips that provider):

  ```bash
  firebase functions:secrets:set CEREBRAS_API_KEY     # paste the key, or: unset
  firebase functions:secrets:set OPENROUTER_API_KEY   # paste the key, or: unset
  firebase functions:secrets:access CEREBRAS_API_KEY  # check (prints the value; don't paste it anywhere)
  ```
-  `gizliOku()` falls back to `process.env` only when the secret isn't bound, e.g. in tests. The emulator reads `functions/.secret.local`, which is gitignored.
- `src/` and the local Next.js app read `process.env`, filled from `.env`.

`defineSecret` requires names that are valid environment variables, so the names are `GROQ_API_KEY` / `GEMINI_API_KEY` / `CEREBRAS_API_KEY` / `OPENROUTER_API_KEY` (not `groq-api-key`). All four exist in `butler-alfred` (Cerebras and OpenRouter since 24 Sep 2026). The CI deploy identity is `firebase-adminsdk-fbsvc@butler-alfred.iam.gserviceaccount.com`, and it has **Secret Manager Admin**. Admin, not just accessor, because the deploy grants the runtime service account access to each secret.

**Do not put any of these keys in `functions/.env`.** The Firebase CLI deploys that file as plain env vars. Cloud Run then rejects the update with `Secret environment variable overlaps non secret environment variable`, which is exactly how the `api` function got stuck after an earlier manual deploy. If that error appears, remove the plain variable from the `api` Cloud Run service (console → Cloud Run → `api` → Edit → Variables & Secrets) and redeploy. Do not "fix" it by reverting to plain `process.env`.
